# Proposal

- **기능:** F-005 재시도와 외부 API 정책
- **단계:** 고도화 5 ([PRD](../../../docs/prd.md) 1장, 3장의 ad 줄, 4장 S-07·S-09, 6장 F-005). F-004의 남은 수용 기준 중 재시도 이벤트 로그도 여기서 채운다. S-10은 좋아요 쓰기 시나리오라 F-003(고도화 6)에서 다룬다.

## Why

[고도화 4 결과](../../../docs/experiments/graceful-degradation.md)에서 S-01~S-09는 모두 가용성과 p99를 지켰지만, PRD 4장이 S-07·S-09에 따로 기대하는 동작은 아직 없다.

- **S-07(ad 429·Retry-After):** feed-service는 429를 받아도 다음 요청에서 ad를 또 부른다. 요청 한도 창마다 한도를 넘은 뒤의 요청이 모두 429로 돌아와, ad 호출 실패율이 0.4968(측정 5분에 약 6만 건)이었다. 외부 API가 "잠시 멈춰 달라"고 한 동안에도 계속 두드려 쿼터와 상대의 신뢰를 깎는다.
- **S-09(user·like 짧은 5xx):** 재시도가 없어 짧은 장애의 실패가 그대로 대체로 이어졌다(like degrade 0.15). 재시도를 그냥 붙이면 장애 동안 하위 서비스로 가는 요청이 시도 횟수만큼 늘어 장애를 키운다(재시도 폭주). 그래서 "재시도 예산"으로 늘어나는 요청에 상한을 둬야 한다.
- **쿼터:** ad는 우리가 고칠 수 없고 요청 한도가 있는 외부 API인데, feed-service는 한도를 모르고 부른다. 429를 받기 전에 스스로 멈춰야 한다(PRD F-005).

## What Changes

- **멱등한 조회만 재시도한다.** post, user, like, recommendation 조회가 5xx나 연결 실패로 빨리 실패하면 지수 backoff와 jitter를 두고 최대 횟수까지 다시 보낸다. 좋아요 토글(멱등하지 않다, F-003 전까지)과 ad(외부 API)는 재시도하지 않는다.
  - **재시도하지 않는 실패:** 4xx(429 포함), 호출 시간 상한 초과, 서킷 열림, 벌크헤드 거절, 요청 시간 예산 초과, 속도 제한, Retry-After 대기. 느린 의존성에 다시 보내면 부하만 키우고, 시간 예산에도 들어가지 않는다.
  - **남은 시간 예산 안에서만** 다시 보낸다. 남은 예산이 그 의존성의 호출 시간 상한과 기다릴 시간보다 짧으면 다시 보내지 않는다. 피드가 응답을 마친 뒤에는 남은 재시도를 보내지 않는다.
  - **서킷이 열려 있으면** 재시도가 바로 멈춘다. 재시도 한 번 한 번이 서킷을 거쳐 실패로 집계된다(아키텍처 5-4의 순서).
- **재시도 예산.** 의존성마다 최근 창(1초)의 원래 호출 수에 비율을 곱한 만큼만 재시도를 허용한다(트래픽이 적을 때를 위한 최솟값이 있다). 예산이 다 되면 다시 보내지 않고 바로 대체한다.
- **Retry-After를 지킨다.** 429에 `Retry-After`(초 또는 HTTP 날짜)가 있으면 그 시각까지 그 의존성을 부르지 않고 바로 실패 처리해 등급대로 대체한다(ad는 광고 영역을 뺀다). 머리글이 없으면 짧은 기본값만큼, 터무니없이 긴 값은 상한까지만 기다린다.
- **ad의 계약 쿼터를 넘기 전에 스스로 멈춘다.** feed-service가 ad 호출에 RateLimiter를 두고, 계약 쿼터(PRD에 가정으로 적는다)의 어느 창에서도 넘지 않게 정한 한도를 넘는 호출은 보내지 않고 바로 대체한다.
- **실패 분류에 우리 쪽 거절 둘을 더한다.** 속도 제한(`rate_limited`)과 Retry-After 대기(`retry_after`). 둘 다 서킷에 세지 않는다.
- **이벤트를 남긴다.** 재시도할 때마다 `downstream_call_retried`(traceId, 의존성, 다음 시도 번호, 앞 시도의 실패 원인, 기다린 시간), Retry-After 대기를 시작할 때 `retry_after_hold_started` 로그를 한 줄 남긴다. 재시도 결정(보냄, 예산 소진, 시간 부족, 횟수 소진), Retry-After로 막은 호출, 속도 제한으로 막은 호출을 지표로 낸다.
- **설정값은 근거와 함께 정한다.** 최대 시도 횟수, backoff, jitter는 시간 예산 계산으로, 재시도 예산 비율은 PRD에 정할 "재시도로 늘어나는 요청 상한"에서, RateLimiter 한도는 계약 쿼터에서 계산해 design과 아키텍처 5-6에 적는다.
- **실험 세트가 재시도와 Retry-After를 판정한다.**
  - 리포트에 의존성별 "요청 배율의 20초 구간 최댓값"과 ad가 돌려준 429 수를 적는다.
  - 판정 기준 둘을 더한다. **요청 배율 기준:** 20초 구간 요청 배율 최댓값이 모든 의존성에서 상한 이하. **Retry-After 기준:** 측정 구간에 ad가 돌려준 429 수가 "요청 한도 창 수 × ad 동시 호출 상한" 이하(429를 받은 순간 이미 나가 있던 호출만 429를 받는다).
  - 고도화 5의 기대: S-01~S-09 모두 가용성·p99·요청 배율 기준을 지키고, S-01은 degrade 비율, S-07은 Retry-After 기준도 지킨다.
  - 대시보드에 재시도·외부 API 행을 더한다.
- **문제를 먼저 재현한다.** 재시도 예산을 끈 구성으로 S-09를 돌려 재시도 폭주(요청 배율)를 기록하고, 예산을 켠 결과와 비교한다. ad RateLimiter 한도를 S-07의 요청 한도보다 낮춘 구성으로 S-07을 한 번 돌려, 스스로 멈추면 429가 0건임을 보인다.
- **고도화 5 결과를 기록한다**(`docs/experiments/retry-policy.md`).

## Capabilities

### New Capabilities

- `retry-policy`: feed-service의 재시도(대상, 실패 종류, 횟수·backoff·jitter, 남은 시간 예산, 재시도 예산, 서킷과의 관계), 429 `Retry-After` 대기, ad 계약 쿼터 RateLimiter, 재시도·대기 이벤트 로그와 지표, 설정으로 바꾸는 값

### Modified Capabilities

- `call-isolation`: "서킷 브레이커의 실패 분류"에 속도 제한과 Retry-After 대기를 세지 않는 것으로 더한다. "4xx는 세지 않는다"의 ad 429는 이제 Retry-After 동안 다시 부르지 않으므로 요청 수를 바꾼다.
- `graceful-degradation`: "중요·선택 등급의 실패는 피드를 실패시키지 않는다"의 "다시 부르지 않는다, 재시도는 F-005"를 "재시도 정책이 끝난 뒤 대체한다"로 바꾼다. 5xx 시나리오의 "한 번만 요청한다"를 최대 시도 횟수로 바꾼다.
- `fault-experiments`: 리포트의 요청 배율 최댓값·ad 429 수, 요청 배율 기준, Retry-After 기준, 고도화 5의 기대, 대시보드 재시도·외부 API 행

## Impact

- **코드:** feed-service `IsolatedCalls`(재시도, Retry-After 대기, RateLimiter를 감싸는 순서), 새 클래스(재시도 정책·예산, Retry-After 대기, 재시도 지표·로그), `DownstreamFailure`(`rate_limited`, `retry_after`), `FeedAssembler`의 `RequestBudget`(재시도가 마감을 알게 한다), `application.yml`(`resilience4j.retry`, `resilience4j.ratelimiter`, 재시도 예산·Retry-After 속성). 하위 서비스 5개는 바뀌지 않는다.
- **API:** `GET /feed` 응답 형식은 그대로다. 재시도가 성공하면 그 영역이 빠지지 않는다. Retry-After 대기·속도 제한 중인 ad는 지금처럼 광고 영역이 빠진다.
- **의존성:** 없다. Resilience4j 스타터(2.4.0)에 Retry와 RateLimiter가 들어 있다.
- **실험:** `run.sh`(요청 배율 최댓값, ad 429 수, 판정 입력 파일), `lib/verdict.sh`(새 기준 둘), `slo.json`(요청 배율 상한), `expectations.json`(고도화 5), 대시보드.
- **테스트:** 테스트 기본 설정(`feed-service/src/test/resources/config/application.yml`)은 재시도를 끈다. 하위 서비스 실패 시 요청 수를 단언하는 기존 테스트가 재시도·예산 상태에 흔들리지 않게 하고, 재시도를 보는 테스트만 켠다(design 결정 12). `FeedCircuitBreakerScenarioTest`의 "4xx는 세지 않는다", `FeedDegradationScenarioTest`의 5xx 시나리오, e2e 판정·리포트 테스트를 델타대로 고친다. 이미 커밋된 테스트라 대화형으로 고친다.
- **문서:** 아키텍처 4-2·5-3~5-6·7-4·9-3·12·13장, PRD F-005·F-004 체크, 3장 ad 줄(계약 쿼터), 10장 "남은 것"(S-09의 재시도 증가 비율 상한)과 "정한 것", `docs/experiments/retry-policy.md`, feed-service `CLAUDE.md`, README의 단계 표
- **하지 않는 것:**
  - 좋아요 토글의 재시도와 S-10. 토글은 멱등하지 않아 재시도하면 상태가 또 뒤집힌다. F-003에서 상태 기반 API로 바꾼 뒤 그 change가 정한다
  - 요청 헤징(느린 호출에 두 번째 요청을 미리 보내기). 재시도는 빨리 실패한 호출만 다룬다
  - 인스턴스 여러 개에서 재시도 예산·쿼터 나누기(PRD 8장). 예산과 RateLimiter는 인스턴스마다다
  - ad-service가 평시에도 계약 쿼터를 강제하는 것. 실험 세트의 ad 한도는 S-07에만 있다. 스스로 멈추는 것은 통합 테스트와 S-07 비교 실행으로 보인다
