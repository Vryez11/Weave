# Proposal

- **기능:** F-001 하위 서비스 호출 격리
- **단계:** 고도화 3 ([PRD](../../../docs/prd.md) 1장, 4장, 6장 F-001). F-004의 남은 수용 기준 중 벌크헤드 스레드 풀의 traceId와 서킷·벌크헤드 이벤트 로그도 여기서 채운다.

## Why

[MVP 기준선](../../../docs/experiments/baseline-mvp.md)에서 선택 등급인 recommendation 하나가 3초 늦어지자(S-02) 피드 요청 거의 전부가 5초 시간 초과로 끝났다. recommendation 커넥션 풀 20개가 차고, 공유 풀 스레드 100개와 대기열 약 500개, Tomcat 스레드 200개가 모두 그 호출을 기다리며 묶였다. 다른 의존성의 호출 지연은 평시와 같았는데도 피드 전체가 멈췄다. 장애를 거둔 뒤에도 쌓인 호출을 비우느라 40초 동안 회복하지 못했다(S-08). 하위 서비스 하나의 장애가 피드 서버의 자원을 묶지 못하게 막아야, 다음 단계(F-002)의 등급별 대체 동작도 시간 안에 할 수 있다.

## What Changes

- **의존성마다 호출 시간 상한을 둔다.** post·user·like 100ms, recommendation·ad 200ms(평시 p99 약 51ms의 2배, 아키텍처 4-3). 큐에서 기다린 시간까지 넣어 잰다. HTTP 클라이언트의 연결·응답·커넥션 대기 타임아웃도 같은 값 이하로 둬, 상한이 지난 호출이 스레드와 연결을 오래 붙잡지 않게 한다.
- **피드 요청 하나에 시간 예산 250ms를 둔다.** post 뒤에 부르는 user·like는 남은 예산 안에서만 기다리고, 예산이 다 되면 기다리지 않는다.
- **의존성마다 벌크헤드(전용 스레드 풀)를 둔다.** 공유 풀 하나를 다섯 의존성이 함께 쓰던 것을 의존성별 풀로 나눈다. 풀이 차면 기다리지 않고 바로 거절한다. recommendation이 느려져도 post·user·like 호출에 쓸 스레드는 줄지 않는다. 좋아요 토글(요청 스레드에서 동기 호출)에도 동시 호출 상한을 둔다.
- **의존성마다 서킷 브레이커를 둔다.** 타임아웃, 연결 실패, 입출력 실패, 5xx는 실패로 세고 4xx는 세지 않는다. 벌크헤드 거절도 세지 않는다. 열리면 그 의존성을 부르지 않고 바로 실패하고, 정해진 시간 뒤 반열림의 시험 호출이 성공하면 닫힌다.
- **실패 응답은 MVP와 같다.** 어느 의존성이든 실패하면(타임아웃, 서킷 열림, 벌크헤드 거절, 예산 초과 포함) 피드는 500이다. 다만 늦어도 시간 예산 안에 응답한다. 등급별 부분 응답과 503은 F-002가 정한다.
- **장애 대응 이벤트를 남긴다.** 호출 실패 로그(`downstream_call_failed`)의 `cause`에 `timeout`, `circuit_open`, `bulkhead_full`, `budget_exhausted`를 더하고, 서킷 상태 전이를 로그 한 줄(`circuit_state_changed`)로 남긴다. Resilience4j 지표(서킷 상태, 벌크헤드 사용량·거절, 타임아웃)를 Prometheus로 내보낸다.
- **벌크헤드 스레드로 넘어갈 때 traceId를 잇는다.** 전파 없이 끊기는 것을 먼저 테스트로 재현하고, 전파를 붙인 뒤 이어지는 것을 확인한다.
- **설정값은 모두 `application.yml`에 두고 환경 변수로 덮어쓸 수 있다.** 값마다 근거(기준선 측정과 계산)를 design과 아키텍처 4-3·5-6에 적는다.
- **실험 세트의 판정을 기준별로 할 수 있게 한다.** 지금은 시나리오마다 "SLO 전체를 지킨다/못 지킨다"만 적을 수 있다. F-001만으로는 실패한 의존성이 여전히 피드를 500으로 만들어 가용성은 못 지키지만, p99는 모든 시나리오에서 지켜야 한다. 기대 결과에 가용성과 p99를 따로 적을 수 있게 하고, 고도화 3의 기대를 "S-01은 모두 지킴, S-02~S-09는 p99만 지킴"으로 바꾼다.
- **리포트와 대시보드에 서킷 상태와 의존성별 벌크헤드 사용량을 넣는다.** 공유 풀 항목은 의존성별 벌크헤드로 바뀐다.
- **고도화 3 결과를 기록한다.** 실험 세트를 돌려 기준선과 비교하고(`docs/experiments/call-isolation.md`), S-08의 복구 시간 목표를 정한다.
- **가상 스레드 비교를 한 번 한다.** S-02를 "플랫폼 스레드 + 스레드 풀 벌크헤드"(기본)와 "가상 스레드 + Semaphore 벌크헤드"로 같은 부하에 돌려 p99, 다른 의존성 호출 지연, 자원 사용량을 기록한다. 기본 구성은 바꾸지 않고, 바꿀지는 결과를 보고 따로 정한다.
- **BREAKING (스펙):** `feed-aggregation`의 "보호 장치 없는 실패 전파"는 없어진다. 느린 하위 서비스를 끝까지 기다리던 동작이 시간 상한 뒤 실패로 바뀐다. MVP 동작을 전제로 쓴 실험 세트의 Compose 시나리오(3초 지연이면 3초 넘게 걸린다, Tomcat 스레드 200이 모두 묶인다 등)도 함께 고친다.

## Capabilities

### New Capabilities

- `call-isolation`: feed-service의 하위 서비스 호출 격리. 의존성별 호출 시간 상한, 요청 시간 예산, 의존성별 벌크헤드, 서킷 브레이커와 실패 분류, 격리 경로를 거치지 않는 호출이 없는 것, 벌크헤드 스레드의 traceId, 장애 대응 이벤트 로그와 지표, 설정으로 바꾸는 값

### Modified Capabilities

- `feed-aggregation`: "보호 장치 없는 실패 전파"를 "하위 서비스 실패는 시간 안에 피드 실패로 끝난다"로 바꾼다(실패 응답 500은 그대로). "서로 기다리지 않는다"는 지연을 시간 상한 안으로 맞춘다. "하위 서비스 호출 실패 로그"의 `cause`에 새 값을 더한다.
- `fault-experiments`: 기대 결과를 기준(가용성, p99)별로 적는 형식과 고도화 3의 기대, 리포트·지표·대시보드의 서킷 상태와 벌크헤드 항목, MVP 동작을 전제로 한 Compose 시나리오(프록시 지연, 짧게 돌린다, 시간 초과된 요청, Tomcat 스레드가 묶여도 긁힌다)

## Impact

- **코드:** feed-service의 `gateway`(격리 적용, 실패 분류), `FeedAssembler`(시간 예산), `client`(의존성별 타임아웃과 커넥션 풀 크기), 새 설정 클래스(서킷 이벤트 로그, traceId 전파). 하위 서비스 5개는 바뀌지 않는다.
- **API:** 응답 형식은 그대로다. 하위 서비스가 느리거나 죽었을 때 피드가 기다리지 않고 500을 준다.
- **의존성:** `io.github.resilience4j:resilience4j-spring-boot4` 2.4.0과 Spring AOP 스타터(Boot 4 이름 `spring-boot-starter-aspectj`)를 feed-service에 더한다. 하네스 규칙 2-2의 "확인" 항목이라 이 change를 승인할 때 함께 확인한다. Boot 4.1.2와의 호환은 첫 구현 작업에서 확인한다(아키텍처 1장).
- **실험:** `experiments/expectations.json`(형식과 고도화 3 기대), `lib/verdict.sh`(기준별 판정), 리포트의 서킷·벌크헤드 항목, Grafana 대시보드의 서킷·벌크헤드 행. 시나리오 정의(장애)는 그대로다.
- **테스트:** MVP 동작을 단언하던 기존 시나리오 테스트(feed 통합 테스트, e2e Compose 테스트, 판정 테스트)를 스펙 델타대로 고친다. 이미 커밋된 테스트라 Ralph 루프가 아니라 대화형 진행(`/opsx:apply`)에서 고친다(하네스 규칙 2-2 훅).
- **문서:** 아키텍처 4-2·4-3·5장·7-3·7-4·9-3·13장, PRD F-001·F-004 체크와 10장 "남은 것"(S-08 복구 시간 목표, 설정값), `docs/experiments/call-isolation.md`, feed-service `CLAUDE.md`
- **하지 않는 것:**
  - 등급별 fallback, 부분 응답 계약, 503, post·user 캐시(F-002). 이 change에서는 실패가 모두 500이다
  - 재시도, ad의 429·Retry-After 처리와 요청 한도(F-005). 429는 4xx라 서킷에 세지 않는 것까지만 한다
  - 하위 서비스에 남은 예산을 넘기는 것(deadline 전파, 아키텍처 4-3)
  - 가상 스레드를 기본 구성으로 바꾸는 것
