# 커밋 컨벤션

## 형식

```
<type>(<scope>): <요약> (F-001)

- <작업 내용 핵심 1>
- <작업 내용 핵심 2>
```

- 요약은 한국어로, "~한다"로 끝나는 현재형 문장으로 쓴다. 마침표는 찍지 않는다.
- 무엇을 건드렸는지보다 무엇이 달라지는지가 보이게 쓴다.
- PRD 기능과 관련 있으면 끝에 기능 ID를 괄호로 붙인다. 여러 개면 `(F-001, F-003)`.
- 여러 영역에 걸친 변경이면 scope를 생략한다.
- 본문에는 작업 내용을 핵심만 1~3개 항목으로 짧게 적는다. 왜 그렇게 했는지가 중요하면 한 줄 덧붙인다. 설정값을 바꿨다면 근거가 된 측정값을 적는다.

## type

| type | 언제 |
|---|---|
| feat | 서비스 동작(응답, 장애 대응, API)을 추가하거나 바꿀 때 |
| fix | 버그를 고칠 때 |
| refactor | 동작은 그대로 두고 구조만 바꿀 때 |
| perf | 성능을 개선할 때 |
| test | 테스트나 장애 실험 세트를 추가·수정할 때 |
| docs | 문서만 바꿀 때 |
| chore | 빌드, 설정, 의존성, CI 등 그 밖의 작업 |

## scope

| scope | 대상 |
|---|---|
| feed | 피드 집계 서비스 (하위 서비스 호출, 장애 격리, 부분 응답) |
| post | 게시글 서비스 |
| user | 작성자 프로필 서비스 |
| like | 좋아요 서비스 (상태 기반 API, 멱등성) |
| recommendation | 추천 서비스 |
| ad | 광고 서비스 (외부 API 역할) |
| observability | 공통 로깅·트레이싱 라이브러리 (`libs/observability`) |
| experiment | 장애 실험 세트 (k6 시나리오, Toxiproxy 장애 설정) |
| build | Gradle 빌드와 컨벤션 플러그인 (`buildSrc`) |
| infra | Docker Compose, 로컬 인프라(MySQL, Redis, Toxiproxy, Loki·Prometheus·Grafana), CI |
| 문서 이름 | docs 커밋일 때: `prd`, `roadmap`, `architecture` 등. OpenSpec 문서는 `spec` ([스펙 관리 규칙](spec.md)) |

## 예시

```
feat(feed): 추천 서비스 호출에 서킷 브레이커를 적용한다 (F-001)

- 타임아웃과 5xx만 실패로 세고 4xx는 무시한다
- 실패율 문턱 50%는 기준선 실험에서 정상 구간 실패율이 1% 미만이었던 것을 근거로 했다
```

```
fix(like): 같은 좋아요 요청이 동시에 오면 카운트가 두 번 오르던 문제를 고친다 (F-003)

- (user_id, post_id) 유니크 제약 위반을 이미 반영된 요청으로 처리한다
- 재시도로 같은 요청이 겹치면 카운트가 실제 좋아요 수보다 커지는 일이 있었다
```

제목 예시:

```
test(experiment): 추천 서비스 3초 지연 시나리오를 추가한다
docs(prd): 의존성 등급과 피드 SLO를 확정한다
chore(build): 서비스와 라이브러리 컨벤션 플러그인을 나눈다
```

## 커밋 단위

- 한 커밋에는 한 가지 변경만 담는다. 기능을 만들다 생긴 리팩터링은 따로 커밋한다.
- 기능 단위로 자주 커밋해서 언제든 되돌릴 수 있게 한다.
- 장애 대응 설정값(타임아웃, 문턱, 풀 크기)을 바꾸는 커밋은 다른 변경과 섞지 않는다. 실험 결과가 어느 변경 때문에 바뀌었는지 가릴 수 있게 한다.
