# 고도화 6 결과: 좋아요 상태 기반 API와 멱등성

고도화 6(`add-idempotent-like`, F-003)에서 토글 좋아요의 문제를 재현하고, 상태 기반 API와 `version` 순서 판단으로 바꾼 뒤 잰 결과다. 설계와 고른 이유는 `add-idempotent-like` design 결정 1~12에 있다.

## 토글의 문제

MVP의 `POST /likes/{postId}/toggle`을 Testcontainers MySQL 9.7에 실제 HTTP로 불렀다(`ToggleBreakageReproductionTest`, 3회 실행). 토글을 없애면서 테스트도 지웠다(design 결정 8). 재현 커밋은 `98f193f`다. 그 커밋을 받아 `./gradlew :like-service:integrationTest -Pkotest.filter.tests='*F-003*'`로 다시 돌려 볼 수 있다.

| 경우 | 보낸 요청 | 결과 (3회) | 뜻 |
|---|---|---|---|
| 재전송 | 사용자 1이 게시글 5에 같은 요청 2번 | 첫 응답 `liked` true·수 1, 둘째 응답 `liked` false·수 0 (3회 모두) | 반영된 요청을 다시 보내면 의도가 뒤집힌다. 타임아웃으로 실패를 받은 클라이언트의 재전송이 바로 이 경우다 |
| 서로 다른 사용자 동시 | 행을 만들어 둔 게시글에 50명이 동시에 | 모두 200. 행 51개, 저장된 수 7 (3회 모두) | 수를 읽고 고쳐 저장해 갱신 44건이 유실됐다. 오류 없이 조용히 어긋난다 |
| 같은 사용자 동시 첫 요청 | 사용자 1이 게시글 7에 20개 동시에 | 500이 17~18개, 200이 2~3개. 남은 행과 수는 0이나 1 | 유니크 위반이 500이 되고, 성공한 요청끼리는 서로 뒤집어 어느 상태로 끝날지 정해지지 않는다 |

동시 50명의 저장된 수가 세 번 모두 7인 것은 HikariCP 최대 10개가 첫 묶음을 같은 값으로 읽고 덮어쓰기 때문으로 보이지만, 원인까지 따로 재지는 않았다.

## S-11 부하 크기

RPS를 올려 가며 쟀다(준비 1분은 0에서 목표 RPS까지 올린다, 측정 1분, 게시글 하나에 반복마다 새 사용자). 앱 수준 지연은 0이고 Compose 자원 상한은 like-service·MySQL 각 CPU 1개다(아키텍처 9-1).

| 방식 | RPS | 실패 | p50 | p99 | 행 잠금 대기 | 대기 시간 합 | 교착 | 불일치 | Hikari 대기 최대 | like CPU 최대 | MySQL CPU 최대 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| atomic | 300 | 0 | 2ms | 1,710ms | 1,504회 | 23,601ms | 0 | 0 | 190 | 0.96 | 0.16 |
| atomic | 400 | 0 | 1ms | 9ms | 922회 | 2,244ms | 0 | 0 | 0 | 0.45 | 0.18 |
| atomic | 500 | 0 | 1ms | 2,910ms | 5,755회 | 52,033ms | 0 | 0 | 189 | 1.02 | 0.43 |
| atomic | 600 | 0 | 1ms | 13ms | 4,035회 | 10,237ms | 0 | 0 | 0 | 0.61 | 0.29 |
| atomic | 800, 1000, 1200, 1500 | 측정 못 함 | | | | | | | | | |
| read-modify-write | 300 | 0 | 1ms | 798ms | 1,132회 | 14,969ms | 0 | 989 | 0 | 1.05 | 0.33 |
| read-modify-write | 400 | 0 | | 50ms | 1,690회 | 8,261ms | 0 | 1,477 | 0 | 0.69 | 0.33 |
| read-modify-write | 600 | 측정 못 함 | | | | | | | | | |

- **400 RPS로 정했다.** 세 방식을 같은 부하로 비교해야 하므로 기준선(`read-modify-write`)이 실패 없이 버티는 단계에서 골랐다. 500 RPS는 재지 않았고 600 RPS는 버티지 못했다. 400 RPS에서 CPU는 한 코어에 닿지 않아(like-service 최대 0.69) 잠금 경합을 재는 범위에 있다.
- "측정 못 함"은 준비 구간에서 시간 초과가 수만 건 나고 like-service가 90초 안에 응답을 돌려주지 못한 경우다. 처리 한계를 넘으면 스스로 회복하지 못했고, 원인까지는 재지 않았다.
- p99는 RPS를 따라 고르게 오르지 않았다. 튄 실행(300, 500 RPS)은 like-service CPU가 한 코어에 닿고 HikariCP 대기가 약 190까지 찼다. 잠금보다 like-service의 순간 막힘(아키텍처 13장)에 가까워 보이지만 가리지는 못했다. 그래서 방식 비교는 측정 2분으로 두 번 돌린다.
- 처음에는 준비 구간부터 목표 RPS를 그대로 줬는데, 막 뜬 like-service에 대기가 쌓여 400 RPS도 "처리 한계"로 잘못 읽었다. 준비 구간을 올리는 방식으로 고친 뒤 위 표를 다시 쟀다.

## S-11 방식 비교

400 RPS, 준비 1분, 측정 2분으로 다섯 구성을 두 번 돌렸다(결과 폴더 `20261109-054233-S-11`, `20261109-055931-S-11`). 분할 8은 두 번 다 막힘에 가려 세 번을 더 쟀다(`20261109-061656-S-11`, `-062028-`, `-062400-`). 측정마다 요청은 약 48,000건이다. 처리량은 고정 부하라 모두 400 RPS이고 실패, 못 보낸 요청, 교착은 모든 구성에서 0이다.

| 구성 | p50 | p99 | 행 잠금 대기 | 대기 시간 합 | 수 불일치 | Hikari 대기 최대 | like CPU 최대 |
|---|---|---|---|---|---|---|---|
| read-modify-write | 1ms | 18ms, 11ms | 3,025회, 2,218회 | 11,547ms, 7,180ms | **2,626건, 1,898건** | 0, 0 | 0.70, 0.52 |
| atomic | 1ms | 11ms, **763ms** | 2,473회, 3,451회 | 6,919ms, 22,848ms | 0, 0 | 0, **189** | 0.44, **0.98** |
| sharded 4 | 1ms | 10ms, 9ms | 328회, 264회 | 712ms, 936ms | 0, 0 | 0, 0 | 0.70, 0.45 |
| sharded 8 (막힌 2회) | 1ms | **2,176ms, 1,624ms** | 2,071회, 1,252회 | 8,302ms, 6,361ms | 0, 0 | **189, 189** | **1.03, 1.02** |
| sharded 8 (깨끗한 3회) | 1ms | 9ms, 9ms, 8ms | 37회, 35회, 10회 | 197ms, 162ms, 12ms | 0, 0, 0 | 0, 0, 0 | 0.40, 0.44, 0.43 |
| sharded 16 | 1ms | 9ms, 9ms | 0회, 0회 | 0ms, 0ms | 0, 0 | 0, 0 | 0.42, 0.42 |

- **읽고 고쳐 저장하기는 조용히 어긋난다.** 실패 없이 2분에 약 2,000~2,600건의 수를 잃었다(약 4~5%).
- **원자적 UPDATE와 카운터 분할은 수가 정확하다.** 모든 실행에서 불일치 0이다.
- **분할은 잠금을 거의 없앤다.** 행 잠금 대기가 atomic 약 2,500~3,500회에서 분할 4는 약 300회, 분할 8은 10~37회, 분할 16은 0회다.
- **그런데 이 부하에서 p99 차이는 없다.** 막히지 않은 실행의 p99는 atomic 11ms, 분할 8~10ms로 같다. 잠금 대기 합이 2분에 약 7초(커넥션 10개 기준 0.6%)라 응답 시간을 움직이지 못한다.
- **막힘은 방식과 관계없다.** like-service CPU가 한 코어에 닿고 HikariCP 대기가 189까지 찬 실행이 atomic에서도 분할 8에서도 나왔고, 같은 분할 8의 다른 세 번은 깨끗했다. 막힘 동안 잠금 대기도 함께 부푼다. 원인은 가리지 못했다(아키텍처 13장의 순간 막힘).
- 처리량 한계는 방식별로 재지 않았다. atomic은 600 RPS까지 실패가 없었고 800 RPS는 버티지 못했다. read-modify-write는 400 RPS까지다.

**고른 것.**

| 항목 | 값 | 이유 |
|---|---|---|
| 기본 방식 | `atomic` | 수가 정확하고, 측정한 부하에서 분할과 응답 시간 차이가 없다. 분할은 쓰기 경로와 조회 합계, 사용자별 칸 선택을 더하지만 얻는 것이 잠금 대기뿐이다 |
| 분할을 켤 때의 칸 수 | 8 | 잠금 대기가 더 줄지 않는 가장 작은 값이다(분할 4 약 300회, 분할 8 10~37회, 분할 16 0회). 8에서 16으로 늘려 줄어드는 대기는 2분에 200ms 안팎이다 |

`read-modify-write`는 운영에서 쓸 이유가 없어 고도화가 끝나면 지울 후보다.

## like-write 상한

리틀의 법칙으로 계산했다. 쓰기 400 RPS(S-11의 부하) × 막히지 않은 실행의 p99 11ms = 동시 4.4개, 여유 2배로 약 9이고, 10은 이 범위를 덮는다. 막힘이 오면 지연이 수백 ms까지 늘어 상한이 차는데, 그때 기다리지 않고 거절해 feed-service의 스레드를 묶지 않는 것이 이 상한의 역할이다. 그래서 값은 10을 유지하고 like 커넥션 풀도 읽기 40 + 쓰기 10 = 50으로 둔다.

### 고도화 5와 비교

이 change는 좋아요 쓰기 경로와 like-service 저장 구조를 바꿨고 피드 조회 경로의 격리·대체·재시도 구성은 그대로다. 그래서 기대는 "고도화 5의 가용성과 p99를 그대로 지킨다"이다. 고도화 5 값은 [고도화 5 결과](retry-policy.md)에서 옮겼다.

|---|---|---|---|---|
| S-01 | 1 → 1 | 89ms → 88ms | 0 → 0 | 1.002 → 1.002 |
| S-02 | 1 → 1 | 201ms → 201ms | recommendation 1 → 1 | 0.08 → 0.005 |
| S-03 | 1 → **0.999233** | 201ms → 201ms | recommendation 1 → 1 | 0.062 → 0.005 |
| S-04 | 1 → 1 | 83ms → 84ms | user 0 → 0 | 0 → 0 |
| S-05 | 1 → 1 | 91ms → 95ms | like 0.9308 → 0.8963 | 0.762 → **1.101** |

- **p99는 모든 시나리오에서 4ms 안으로 같다.** 저장 구조를 바꿨지만 조회 지연은 달라지지 않았다.
- **S-03 가용성 0.999233.** SLO(99.9%) 안이지만 고도화 5의 1보다 낮아 따로 봤다. 실패 92건은 모두 503이고, 측정 시작 1.3~1.8초 뒤(06:46:18.8~19.3) 약 0.5초에 몰렸다. 같은 순간 post·like·ad가 함께 실패했고(degrade 0.0008·0.0011·0.001) post 캐시 읽기 오류가 약 110건 올랐다. 고도화 4·5에 기록한 "장애 시작 순간의 feed-service 멈춤"과 "post 실패와 같은 순간의 캐시 읽기 실패"가 겹친 모습이다. 쓰기 경로나 like-service 저장 구조가 원인이라는 신호는 없다. 다만 멈춤의 원인 자체는 이번에도 가르지 못했다(아키텍처 13장).
- **S-05 like 요청 배율 최댓값 0.762 → 1.101.** 다시 부른 횟수가 2,164번에서 3,013번으로 늘었다. 상한 1.2 안이고 재시도 예산이 막은 횟수도 5,430번에서 8,745번으로 늘었다. 서킷이 닫혀 있던 구간이 달라서 생길 수 있는 차이지만, 이 change가 like 조회 응답을 바꾼 것과 무관한지는 한 번의 실행으로 가를 수 없다.
- **S-07 ad 요청 배율 최댓값 0.549 → 0.661.** ad-service가 돌려준 429는 30건 → 29건(허용 1,240 이내)으로 같다.
