# 고도화 6 결과: 좋아요 상태 기반 API와 멱등성

고도화 6(`add-idempotent-like`, F-003)에서 토글 좋아요의 문제를 재현하고, 상태 기반 API와 `version` 순서 판단으로 바꾼 뒤 잰 결과다. 설계와 고른 이유는 `add-idempotent-like` design 결정 1~12에 있다.

## 토글의 문제

MVP의 `POST /likes/{postId}/toggle`을 Testcontainers MySQL 9.7에 실제 HTTP로 불렀다(`ToggleBreakageReproductionTest`, 3회 실행). 토글을 없애면서 테스트도 지웠다(design 결정 8). 재현 커밋은 `98f193f`다. 그 커밋을 받아 `./gradlew :like-service:integrationTest -Pkotest.filter.tests='*F-003*'`로 다시 돌려 볼 수 있다.

| 경우 | 보낸 요청 | 결과 (3회) | 뜻 |
|---|---|---|---|
| 재전송 | 사용자 1이 게시글 5에 같은 요청 2번 | 첫 응답 `liked` true·수 1, 둘째 응답 `liked` false·수 0 (3회 모두) | 반영된 요청을 다시 보내면 의도가 뒤집힌다. 타임아웃으로 실패를 받은 클라이언트의 재전송이 바로 이 경우다 |
| 서로 다른 사용자 동시 | 행을 만들어 둔 게시글에 50명이 동시에 | 모두 200. 행 51개, 저장된 수 7 (3회 모두) | 수를 읽고 고쳐 저장해 갱신 44건이 유실됐다. 오류 없이 조용히 어긋난다 |
| 같은 사용자 동시 첫 요청 | 사용자 1이 게시글 7에 20개 동시에 | 500이 17~18개, 200이 2~3개. 남은 행과 수는 0이나 1 | 유니크 위반이 500이 되고, 성공한 요청끼리는 서로 뒤집어 어느 상태로 끝날지 정해지지 않는다 |

동시 50명의 저장된 수가 세 번 모두 7인 것은 HikariCP 최대 10개가 첫 묶음을 같은 값으로 읽고 덮어쓰기 때문으로 보이지만, 원인까지 따로 재지는 않았다.

## S-11 부하 크기

RPS를 올려 가며 쟀다(준비 1분은 0에서 목표 RPS까지 올린다, 측정 1분, 게시글 하나에 반복마다 새 사용자). 앱 수준 지연은 0이고 Compose 자원 상한은 like-service·MySQL 각 CPU 1개다(아키텍처 9-1).

| 방식 | RPS | 실패 | p50 | p99 | 행 잠금 대기 | 대기 시간 합 | 교착 | 불일치 | Hikari 대기 최대 | like CPU 최대 | MySQL CPU 최대 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| atomic | 300 | 0 | 2ms | 1,710ms | 1,504회 | 23,601ms | 0 | 0 | 190 | 0.96 | 0.16 |
| atomic | 400 | 0 | 1ms | 9ms | 922회 | 2,244ms | 0 | 0 | 0 | 0.45 | 0.18 |
| atomic | 500 | 0 | 1ms | 2,910ms | 5,755회 | 52,033ms | 0 | 0 | 189 | 1.02 | 0.43 |
| atomic | 600 | 0 | 1ms | 13ms | 4,035회 | 10,237ms | 0 | 0 | 0 | 0.61 | 0.29 |
| atomic | 800, 1000, 1200, 1500 | 측정 못 함 | | | | | | | | | |
| read-modify-write | 300 | 0 | 1ms | 798ms | 1,132회 | 14,969ms | 0 | 989 | 0 | 1.05 | 0.33 |
| read-modify-write | 400 | 0 | | 50ms | 1,690회 | 8,261ms | 0 | 1,477 | 0 | 0.69 | 0.33 |
| read-modify-write | 600 | 측정 못 함 | | | | | | | | | |

- **400 RPS로 정했다.** 세 방식을 같은 부하로 비교해야 하므로 기준선(`read-modify-write`)이 실패 없이 버티는 단계에서 골랐다. 500 RPS는 재지 않았고 600 RPS는 버티지 못했다. 400 RPS에서 CPU는 한 코어에 닿지 않아(like-service 최대 0.69) 잠금 경합을 재는 범위에 있다.
- "측정 못 함"은 준비 구간에서 시간 초과가 수만 건 나고 like-service가 90초 안에 응답을 돌려주지 못한 경우다. 처리 한계를 넘으면 스스로 회복하지 못했고, 원인까지는 재지 않았다.
- p99는 RPS를 따라 고르게 오르지 않았다. 튄 실행(300, 500 RPS)은 like-service CPU가 한 코어에 닿고 HikariCP 대기가 약 190까지 찼다. 잠금보다 like-service의 순간 막힘(아키텍처 13장)에 가까워 보이지만 가리지는 못했다. 그래서 방식 비교는 측정 2분으로 두 번 돌린다.
- 처음에는 준비 구간부터 목표 RPS를 그대로 줬는데, 막 뜬 like-service에 대기가 쌓여 400 RPS도 "처리 한계"로 잘못 읽었다. 준비 구간을 올리는 방식으로 고친 뒤 위 표를 다시 쟀다.
