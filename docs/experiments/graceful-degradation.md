# 고도화 4 결과: 등급별 Graceful Degradation

고도화 4(`add-graceful-degradation`, F-002)에서 하위 서비스 실패를 의존성 등급대로 대체한 뒤 잰 장애 실험 결과다. [고도화 3 결과](call-isolation.md), [MVP 기준선](baseline-mvp.md)과 같은 시나리오·같은 부하로 재서 비교한다.

- 결과 원본(`experiments/results/`)은 커밋하지 않는다. 아래 표는 각 실행의 `report.json`과 같은 구간의 Prometheus 값에서 옮겼고, 결과 폴더 이름을 함께 적는다.
- 대체 동작과 설정값의 근거는 [아키텍처](../architecture.md) 6장과 `add-graceful-degradation` design 결정 1~16에 있다.
- 피드 지연(p50·p95·p99)은 k6가 요청 앞뒤로 잰 경과 시간(`feed_latency`, 밀리초)이고 실패한 요청을 포함한다. degrade 비율은 측정 구간의 200 응답 중 그 의존성이 `degradation.missing`이나 `degradation.stale`에 있던 비율이다(`lib/degrade.sh`).

S-01의 p99 차이(89 → 97ms)는 고도화 3까지의 잡음 범위(89~95ms)를 조금 넘는다. 평시 순간 막힘이 실패 대신 degrade로 바뀌어 응답이 나가면서 그 요청의 지연이 p99에 남는 것으로 보인다(아래 "평시 like").

### 실패한 의존성만 빠지고 피드는 응답한다 (S-02~S-05, S-07, S-08)

- **가용성 0 → 1.** 선택 등급(recommendation, like, ad)이 실패하면 그 영역만 빠진 200이다. degrade 비율이 실패한 의존성에만 오르고(S-02·S-03 recommendation 1, S-05 like 0.93, S-07 ad 0.50) 다른 의존성은 0에 가깝다.
- **p99는 고도화 3과 같다.** 대체는 응답을 늦추지 않는다. S-02·S-03·S-08의 200ms는 recommendation 상한에서 끊긴 요청이다.
- **S-05:** like 서킷이 열린 동안은 모든 요청에서 like가 빠져 degrade 비율이 0.93이다(에러율 50%보다 높다). 고도화 3에서는 서킷이 열린 동안 피드가 실패해 가용성이 0.064로 기준선보다 나빴는데, 이제는 같은 서킷 동작이 사용자에게 `UNKNOWN`으로만 보인다.
- **S-08:** 장애를 거둔 뒤 recommendation 서킷이 닫히고 degrade가 평시로 돌아왔다. 가용성은 장애 동안에도 1이라 SLO 기준의 복구 시간은 0초다(리포트 `recovery`). degrade 비율 0.40은 장애 120초와 서킷이 닫히기까지의 몫이다.

- **S-09:** 10초짜리 user·like 5xx 장애 세 번 동안 user는 캐시로(18,181건), like는 `UNKNOWN`으로(18,106건, degrade 0.15) 대체돼 가용성이 0.81 → 1이다. 장애마다 서킷이 열렸다 닫혔고, 장애를 거둔 뒤 열림 유지만큼 이어지던 실패도 이제 대체로 가려진다. p99도 130 → 87ms로 줄었다. 하위 서비스로 가는 요청 배율은 user·like 0.90이고 재시도가 없어 1을 넘지 않는다(재시도 예산은 F-005).

### 작성자는 로컬 캐시로 채운다 (S-04)

- user-service가 측정 내내 다운이었지만 user 영역은 모두 "캐시로 채움"이었다(`weave_feed_sections_total{section="user",outcome="cached"}` 119,993, `missing` 0). 준비 구간 1분이 작성자 50명을 모두 캐시에 넣었다.
- **한계:** 실험 데이터가 고정이라(게시글 200개, 작성자 50명, 최신 목록이 늘 같다) 적중률이 100%다. 실제 서비스에서는 캐시에 없는 작성자가 `unknown`이 되고, 그 비율은 이 실험으로 알 수 없다.

### 게시글은 stale 캐시로 대체한다 (S-06)

- post-service가 측정 내내 다운이었지만 응답의 99.986%가 200이었다. 모두 준비 구간에 채운 post 캐시로 만든 stale 응답이다(post degrade 1, `weave_post_cache_reads_total{outcome="hit"}` 119,981). 측정 5분이 stale 허용 10분 안이라 만료(`expired`)는 없었다.
- p99는 63ms로 오히려 평시보다 짧다. post가 연결 거부로 바로 실패하고(서킷이 열린 뒤에는 부르지도 않는다) Redis 읽기가 1ms 안쪽이라, post 호출 50ms 남짓을 Redis 읽기로 바꾼 셈이다.
- **503 17건(0.014%):** 모두 캐시 읽기 오류(`reason` `cache_error`)다. 그중 6건은 Redis GET이 30ms 상한을 넘겨 취소된 것이고(`lettuce_seconds{error="CancellationException"}`), 나머지 11건은 Lettuce 명령 지표에 남지 않은 실패다. 가용성 SLO(99.9%) 안이다. 원인은 아래 "남은 것"에서 본다.
- Redis는 400 RPS 읽기에서 CPU가 한 코어의 약 3%였다(design 결정 6의 측정).

### 평시 like (S-01)

- S-01의 degrade 비율 0.0052는 거의 like다(0.0051, 617건). 고도화 3에서 피드 실패로 드러나던 like-service의 순간 막힘(고도화 3 "남은 것")이 이제 like 영역이 빠진 응답으로 바뀌었다. degrade 기준(1%)의 절반 남짓이다.
- 같은 현상이 S-04(like 0.0332, like 서킷 열림 → 닫힘)와 준비 실행(like 0.0829)에서도 보였다. 장애를 넣지 않은 like가 열린 서킷만큼 빠진다. 가용성에는 영향이 없지만 평시 여유를 깎는다.
- S-01의 503 6건은 post 호출이 실패한 같은 순간 캐시 읽기도 오류였던 요청이다(4.4의 평시 측정과 같은 모습, design 결정 16).

## 남은 것

- **like-service의 순간 막힘.** 고도화 3부터 이어진다(평시 like degrade 0.5%, S-04 3.3%). 이제는 가용성이 아니라 degrade 비율로 드러난다. 원인(메모리 압박, 관찰 파이프라인 포화, 호스트 순간 멈춤)은 아직 가리지 못했다.
- **post 실패와 캐시 읽기 실패가 같은 순간에 오는 것.** S-01의 503 6건, S-06의 17건이다. feed-service 쪽 순간 멈춤이 두 호출을 함께 늦추는 것으로 보이지만, S-06의 11건은 Lettuce 지표에 남지 않아 무엇으로 실패했는지 모른다. 읽기 오류를 원인별로 세는 지표(`weave.post.cache.reads`에 오류 종류)가 있으면 가를 수 있다.
- **S-09의 재시도와 S-07의 Retry-After.** 고도화 5(F-005)가 다룬다. 이 change에서는 대체만으로 가용성을 지켰다.
