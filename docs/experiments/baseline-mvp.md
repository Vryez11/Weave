# MVP 기준선

고도화 2(`add-fault-experiments`, F-007)에서 잰 MVP 구성의 장애 실험 결과다. 장애 대응(F-001~F-005)을 넣기 전의 출발점이고, 이후 단계의 결과는 이 문서의 값과 비교한다. 정하는 방법은 `add-fault-experiments` design 결정 12에 있다.

- 결과 원본(`experiments/results/`)은 커밋하지 않는다. 아래 표는 각 실행의 `report.json`에서 옮긴 값이고, 결과 폴더 이름을 함께 적는다.
- 시나리오 정의, 판정, 리포트 항목은 [아키텍처](../architecture.md) 9장에 있다.
- 피드 지연(p50·p95·p99)은 k6가 요청 앞뒤로 잰 경과 시간(`feed_latency`, 밀리초 단위)이다. 실패한 요청과 시간 초과된 요청(5초)을 포함한다.

## 실험 RPS

S-01(장애 없음)을 100·200·300·400 RPS로 돌려, 아래를 모두 채우는 가장 높은 값을 골랐다.

- S-01이 SLO(가용성 99.9%, p99 300ms)를 지킨다

- 이 네 번은 지연 측정을 `feed_latency`로 바꾸기 전(k6 `http_req_duration`)에 쟀다. 장애가 없는 S-01에는 시간 초과가 없어 두 지표가 같은 요청을 재고, 아래 잡음의 p99(90~95ms)와도 같은 범위다. 고르는 기준(SLO와 300ms의 거리, 보내지 못한 요청, CPU)은 바뀌지 않아 다시 재지 않았다.

**실험 RPS는 400이다**(`experiments/config.json`). 네 값 모두 기준을 채웠고, 규칙대로 가장 높은 값을 골랐다.

- 400 RPS는 MVP 풀 크기의 근거였던 200 RPS(공유 풀 100, 라우트당 커넥션 20)의 두 배다. 평시에도 공유 풀 대기열과 커넥션 풀 대기가 잠깐씩 생기지만 p99는 100 RPS와 3ms 안쪽으로 같다. 장애 시나리오에서 자원이 차는 모습이 더 빨리 드러난다.
- 400 RPS보다 높은 값은 재지 않았다. design 결정 12의 후보가 100~400이다.

### 장애가 피드 전체로 번진 모습

**느린 선택 의존성 하나가 피드 전체를 멈춘다(S-02, S-03, S-08).** recommendation은 선택 등급이라 PRD대로라면 추천 섹션만 빠져야 하지만, MVP에서는 피드 요청 거의 전부가 k6의 5초 시간 초과로 끝났다.

- 묶이는 순서: recommendation 커넥션 풀 20개가 먼저 찬다. S-02에서 20개로 3초짜리 호출을 돌리면 초당 약 6.7번만 부를 수 있는데, 피드는 초당 400번 부른다. 공유 풀 스레드 100개 중 20개는 응답을, 80개는 커넥션을 기다린다(커넥션 풀 대기 80). 다른 의존성 호출도 같은 공유 풀을 써서 대기열에 쌓인다(최대 약 500). Tomcat 스레드 200개는 공유 풀의 결과를 기다리며 모두 묶인다(평균 197).
- 다른 의존성은 정상이다. S-02에서 post·ad 호출 p99는 64ms, user·like는 82~93ms로 평시 근처다. 막힌 것은 호출을 기다리는 스레드와 대기열이다.
- S-03(무응답)은 S-02와 같은 모양이고, 묶인 호출은 HttpClient 응답 타임아웃 3분까지 풀리지 않는다. recommendation 호출 p99가 30,000ms로 나오는 것은 Micrometer 히스토그램의 상한이 30초여서이고, 실제로는 더 길다.
- CPU는 오히려 낮다(0.17~0.18). 자원이 계산이 아니라 기다림에 묶여 있다는 뜻이다. 실험 RPS를 고를 때 CPU 0.7 미만을 기준으로 둔 것도 이 구분을 지키려는 것이었다.

**장애를 거둬도 바로 돌아오지 않는다(S-08).** 120초에 무응답을 거둔 뒤 10초 구간은 아래와 같다.

| 구간(초) | p99 | 가용성 |
|---|---|---|
| 120~130 | 5,002ms | 0 |
| 130~140 | 5,007ms | 0 |
| 140~150 | 5,002ms | 0.377 |
| 150~160 | 3,106ms | 1 |
| 160~170 | 96ms | 1 |

160초 구간부터 끝까지 SLO를 지켜 복구 시간은 40초다. 거둔 뒤에도 공유 풀 대기열에 쌓인 호출(최대 400)과 다섯 의존성의 커넥션 풀(모두 20 사용 중, 대기 3~80)을 비우는 동안 새 요청이 기다렸다.

**빨리 실패하는 장애는 자원을 묶지 않지만 피드를 실패시킨다(S-04, S-05, S-06, S-07, S-09).** 연결 거부(S-04, S-06)나 즉시 오는 에러(S-05, S-07, S-09)에서는 Tomcat·공유 풀·커넥션 풀이 평시 수준이다. 대신 MVP는 실패를 처리하지 않아 실패한 의존성의 비율만큼 피드가 500이 된다.

- 가용성은 넣은 장애의 크기와 같다. S-05·S-07은 0.50(에러율 50%, 한도는 RPS×10초의 절반), S-09는 0.90(5분 중 10초씩 세 번)이고, S-04·S-06은 0이다.
- user(중요 등급)와 like·ad(선택 등급)의 실패도 필수인 post의 실패와 똑같이 피드 전체를 실패시킨다. F-002(등급별 degradation)가 다룰 부분이다.
- S-09의 복구 시간 0초: 에러를 거두자 다음 구간부터 바로 SLO를 지킨다. 묶인 자원이 없어서다.

### 측정에서 고친 것

이 기준선은 측정 결함 두 가지를 고친 뒤(tasks 6.9~6.13) 다시 잰 것이다. 첫 실행(`20261106-061247-S-01`~`20261106-070435-S-09`, 커밋 `4e9101f`)의 판정은 같았지만 아래 값이 실제와 달라 쓰지 않는다.

- S-02·S-03의 p50이 0ms였다. 시간 초과된 요청 약 11만 개의 k6 `http_req_duration`이 0으로 남았다. 지연을 요청 앞뒤 경과 시간(`feed_latency`)으로 바꿨다.
- S-02·S-03은 측정 구간 거의 내내, S-08은 처음 150초 동안 Prometheus가 feed-service를 긁지 못했다. 업무 요청이 Tomcat 스레드를 모두 묶어 같은 커넥터의 `/actuator/prometheus`도 막혔다. Compose에서 feed-service의 Actuator를 관리 포트 8090으로 떼고, 리포트에 지표 수집 비율을 적게 했다.
