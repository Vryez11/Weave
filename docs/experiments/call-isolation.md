# 고도화 3 결과: 하위 서비스 호출 격리

고도화 3(`add-call-isolation`, F-001)에서 하위 서비스 호출에 시간 상한, 요청 시간 예산, 의존성별 벌크헤드, 서킷 브레이커를 넣은 뒤 잰 장애 실험 결과다. [MVP 기준선](baseline-mvp.md)과 같은 시나리오·같은 부하로 재서 비교한다.

- 결과 원본(`experiments/results/`)은 커밋하지 않는다. 아래 표는 각 실행의 `report.json`에서 옮긴 값이고, 결과 폴더 이름을 함께 적는다.
- 시나리오 정의, 판정, 리포트 항목은 [아키텍처](../architecture.md) 9장, 설정값과 근거는 아키텍처 5-6과 `add-call-isolation` design 결정 3~7·15·16에 있다.
- 피드 지연(p50·p95·p99)은 k6가 요청 앞뒤로 잰 경과 시간(`feed_latency`, 밀리초)이다. 실패한 요청을 포함한다.

### 느린 선택 의존성이 더는 피드 전체를 멈추지 않는다 (S-02, S-03, S-08)

- **피드 p99 5,002ms → 201ms.** recommendation 호출은 200ms 상한에서 끊기고, 서킷이 열린 뒤에는 부르지 않는다. recommendation이 받은 요청은 피드 요청의 1%(S-02 요청 배율 0.01)뿐이다. 나머지는 반열림 시험 호출이다.
- **다른 의존성은 평시와 같다.** S-02에서 post·user·like·ad 호출 p99는 50.5~51.9ms로 S-01(51.0~53.3ms)과 같다. 기준선 S-02에서는 같은 공유 풀의 대기열에 묶여 post·ad 64ms, user 93ms, like 82ms였다.
- **자원이 묶이지 않는다.** Tomcat 사용 중 스레드 최댓값은 200 → 45~47이다. 묶이는 것은 recommendation 벌크헤드 40개와 그 커넥션 풀 40개뿐이고, 기준선의 공유 풀 대기열(최대 약 500)과 다른 의존성의 커넥션 대기는 없다.
- **가용성은 아직 0이다.** 고도화 3에서는 실패한 의존성이 여전히 피드를 500으로 만든다(`feed-aggregation` "하위 서비스 실패는 시간 안에 피드 실패로 끝난다"). 등급별 부분 응답은 고도화 4(F-002)가 맡는다. 기대 결과도 그렇게 적었다.

### 빨리 실패하는 장애는 서킷 때문에 실패가 더 길어진다 (S-05, S-09)

- **S-05:** like 에러율 50%가 서킷 문턱(50%) 근처라 서킷이 열렸다 닫혔다 했다. 열린 동안은 like 호출이 모두 실패해, 기준선에서 절반은 성공하던 피드(가용성 0.50)가 거의 모두 실패했다(0.064). PRD 4장의 기대("실패가 이어지면 서킷이 열린다")대로이고, like가 선택 등급이라 F-002에서 `UNKNOWN` 부분 응답이 되면 피드는 성공한다.
- **S-09:** 10초짜리 5xx 장애마다 user·like 서킷이 열리고, 장애를 거둔 뒤에도 열림 유지(최대 5초)만큼 실패가 이어져 가용성이 0.90 → 0.81로 낮아졌다. 장애를 거둔 뒤 SLO를 다시 지키기까지는 10초다. 재시도와 함께 고도화 5(F-005)가 다시 다룬다.

### S-08의 복구 시간

- 장애(recommendation 무응답)를 120초에 거둔 뒤 **130초 구간부터 SLO를 지켰다(10초).** 목표 20초(PRD 10장) 안이고 기준선 40초의 4분의 1이다. 기준선에서는 공유 풀 대기열과 커넥션 풀에 쌓인 호출을 비우느라 늦었는데, 고도화 3에서는 쌓인 호출이 없다.
- 리포트의 복구 시간이 50초인 것은 **160초 구간에 장애와 관계없는 like가 따로 막혀서**다(구간 가용성 0.0035). 그 순간 feed-service에서 like 호출 타임아웃이 초당 339건으로 치솟고 like 서킷이 열렸다(07:15:38). like-service 자체의 요청 처리 최대가 0.7초까지 늘었지만, CPU(0.3)·DB 커넥션(대기 0)·GC(큰 멈춤 없음)는 평소와 같았다. 같은 때 like-service가 트레이스 스팬을 Alloy로 보내지 못해 버렸다는 경고가 이어졌다(07:15:31~39). 원인은 아래 "남은 것"에서 본다.

## 이 단계에서 찾아 고친 것

설정값을 넣은 뒤 S-01을 재다가 MVP에서는 보이지 않던 문제 둘을 찾았다. 둘 다 시간 상한이 생겨 짧은 멈춤이 곧 실패가 되면서 드러났다.

| 문제 | 증거 | 고친 것 |
|---|---|---|
| **콜드 스타트 고리.** Compose를 막 띄운 직후의 like-service가 느려 서킷이 열리고, 열린 동안 트래픽이 가지 않아 데워지지 못한 채 약 100초 동안 열림·닫힘을 되풀이했다 | `20261107-040311-S-01`: 가용성 0.892, 측정 첫 40초 가용성 0.05~0.48 | `run-all.sh`가 첫 시나리오 전에 S-01 준비 실행(측정 1분)으로 하위 서비스를 데운다(design 결정 10). 데운 뒤 `20261107-041019-S-01`은 가용성 0.999492 |
| **Serial GC의 1초 멈춤과 서킷의 증폭.** 자원 상한 때문에 JVM이 Serial GC를 골라 like-service에 1.05초 Full GC가 생겼고, 판단 창(최근 호출 100개 = 0.25초)이 그 1초로 차서 서킷이 5초 열렸다. like 호출 2,045건이 막혀 피드가 실패했다 | `20261107-045536-S-01`: 가용성 0.982342 | 서비스 JVM을 G1로 고정하고(design 결정 15. G1 최대 멈춤 80ms, ZGC는 이 메모리 상한에서 서비스가 응답하지 못함), 서킷 판단 창을 최근 10초로 바꿨다(결정 16) |

## 남은 것

- **like-service의 순간 막힘.** 장애를 넣지 않은 like가 S-04(like 호출 p99 98.4ms, like 서킷 열림), S-08(160초), S-09(like 호출 p99 105.7ms)에서 잠깐씩 느려졌다. like-service는 G1에서 컨테이너 메모리가 512MiB 중 약 493~506MiB이고, 같은 때 스팬 내보내기 실패가 있었다. 메모리 압박, 관찰 파이프라인(Alloy CPU 0.5) 포화, 호스트 쪽 순간 멈춤 중 무엇인지 아직 가리지 못했다. 고도화 3의 기대 결과에는 영향이 없었지만(S-08은 p99를 지켰다), 평시 여유를 깎는다.

## 가상 스레드 비교 (S-02)

PRD F-001의 마지막 수용 기준이다. S-02(recommendation 3초 지연)를 같은 날 같은 상태(하위 서비스를 데운 뒤, 400 RPS, 준비 1분 + 측정 5분)에서 두 구성으로 한 번씩 돌렸다. 가상 스레드 구성은 `FEED_SPRING_APPLICATION_JSON='{"weave.isolation.bulkhead-type":"semaphore","spring.threads.virtual.enabled":true}'`로 feed-service 컨테이너를 새로 만들어 띄웠다(design 결정 11). 벌크헤드 상한은 둘 다 의존성마다 40이다.

| 항목 | 플랫폼 스레드 + ThreadPool 벌크헤드 (기본) | 가상 스레드 + Semaphore 벌크헤드 |
|---|---|---|
| 결과 폴더 | `20261107-080959-S-02` | `20261107-081631-S-02` |
| 판정 | p99 충족·가용성 미충족, 기대와 같음 | 같음 |
| 피드 p50 · p95 · p99 | 49 · 77 · 201ms | 50 · 78 · 201ms |
| post · user · like · ad 호출 p99 (격리 효과) | 50.8 · 51.1 · 52.3 · 50.9ms | 50.6 · 51.3 · 52.8 · 51.4ms |
| feed-service 플랫폼 스레드 수 (`jvm_threads_live_threads`) | 436 | 32 |
| Tomcat 사용 중 스레드 최댓값 | 42 | 지표 없음(가상 스레드라 Tomcat 스레드 풀 지표가 -1) |
| feed-service CPU 평균 · 최댓값 | 0.28 · 0.45 | 0.33 · 0.47 |
| 힙 · 비힙 최댓값 | 196 · 101MB | 184 · 103MB |
| recommendation 시간 상한 초과 · 벌크헤드 거절 | 1,104 · 536 | 1,700 · 1,154 |
| recommendation 서킷이 막은 호출 | 118,381 | 117,175 |

- **격리 효과는 같다.** 피드 p99와 다른 의존성의 호출 지연이 잡음 안에서 같다. 두 구성 모두 느린 recommendation을 상한 40으로 가두고, 서킷이 열린 뒤에는 거의 부르지 않는다.
- **플랫폼 스레드 수가 436 → 32로 준다.** 기본 구성의 436은 Tomcat 200, 벌크헤드 5 × 40 = 200과 그 밖의 스레드다. 가상 스레드 구성에서는 요청과 하위 호출이 가상 스레드에서 돌아, 플랫폼 스레드는 캐리어와 관리 스레드만 남는다. 메모리는 힙·비힙 모두 비슷하다. 플랫폼 스레드의 스택은 예약일 뿐 실제로 쓰는 양이 적어서다.
- **CPU는 가상 스레드 구성이 약 15% 높다**(평균 0.28 → 0.33). 측정 한 번이라 잡음일 수도 있다. 기준 0.7과는 둘 다 거리가 멀다.
- **recommendation 거절과 시간 상한 초과는 가상 스레드 구성이 많다.** 서킷이 열리기 전과 반열림 동안 recommendation을 부른 수가 달라 생긴 차이로 보인다. 두 구성 모두 피드 결과(가용성 0, p99 201ms)는 같다.
- **결론: 기본 구성을 바꾸지 않는다.** 400 RPS에서 기본 구성은 스레드에 묶이지 않는다(Tomcat 사용 중 최대 42 / 200). 가상 스레드가 주는 이득(플랫폼 스레드 수)이 이 부하에서는 결과를 바꾸지 않고, 바꾸면 Tomcat 스레드 지표처럼 실험 리포트의 자원 항목도 다시 정해야 한다. 동시 요청이 Tomcat 최대 스레드에 닿는 부하에서 다시 비교할 만하다.
