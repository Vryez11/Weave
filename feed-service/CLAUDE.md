# feed-service

- 하위 서비스 호출은 `com.weave.feed.gateway`의 Gateway Bean을 거친다. 조회 메서드는 `IsolatedCalls.call("<의존성>") { ... }`로만 부른다(재시도 루프 `RetryLoop` → Retry-After 대기 → 서킷 → RateLimiter(인스턴스가 있는 ad만) → TimeLimiter → ThreadPool 벌크헤드, 실패 로그는 마지막 시도에 한 번). 재시도의 마감은 `RequestBudget.call`이 `start()` 동안 두는 `RequestDeadline`(ThreadLocal)에서 읽으므로 Gateway는 `IsolatedCalls.call`을 그 안에서 동기로 불러야 한다. 요청 스레드에서 부르는 동기 호출(토글)은 `IsolatedCalls.callBlocking("<의존성>", "<Semaphore 벌크헤드>") { ... }`(서킷 → Semaphore 벌크헤드, TimeLimiter 없음, 실패 로그 한 줄)다. Semaphore 벌크헤드 이름은 `IsolatedCalls.BLOCKING_BULKHEADS`에 더해야 시작할 때 꺼내 둔다. 새 호출 경로도 같은 실패 로그를 남겨야 한다.
- `weave.isolation.bulkhead-type: semaphore`(`IsolationProperties`)면 `IsolatedCalls.call`이 ThreadPool 벌크헤드 대신 같은 이름의 Semaphore 벌크헤드(`resilience4j.bulkhead.instances.<의존성>`)로 자리를 잡고 `applicationTaskExecutor`에서 부른다. 이 경로의 trace는 공유 풀의 `propagate-context`만 잇는다. 호출 자체에 문맥을 펼치면 `FeedTracePropagationOffTest`(끊김 기록)가 깨진다. 결과 쪽(`completingIn`)은 두 모드가 같다.
- 격리 인스턴스 이름은 `IsolatedCalls.DEPENDENCIES`(HTTP 서비스 그룹 이름과 같다)이고 시작할 때 레지스트리에서 꺼내 둔다. 다른 이름으로 부르면 `NoSuchElementException`이다. 시간 상한 초과는 `isolation-timeout` 스레드에서 끝나 MDC가 없으므로, 실패 로그는 `call`을 부른 스레드의 MDC를 받아 두었다가 남긴다.
- 벌크헤드 스레드의 traceId는 `TraceContextPropagator`(`thread-pool-bulkhead.configs.default.context-propagators`)가 넘긴다. 벌크헤드 스레드는 결과 future를 끝내기 전에 문맥을 닫으므로, `IsolatedCalls.call`이 부른 스레드의 스냅샷(`traceContexts.captureAll()`)과 MDC를 펼친 채로 TimeLimiter의 결과를 끝낸다(`completingIn`). 그래야 서킷의 결과 기록(상태 전이 로그)과 `thenCompose`로 이어 붙인 호출(post 뒤 user·like)이 같은 trace를 잇는다. future를 다른 스레드에서 끝내는 경로를 더하면 같은 방법을 쓴다.
- 서킷 상태 전이 로그(`circuit_state_changed`)는 `CircuitStateLog`가 레지스트리의 모든 서킷에 건다(이미 있는 것 + `onEntryAdded`). 서킷을 새로 만들어도 따로 걸 필요가 없다.
- 요청 시간 예산은 `FeedAssembler`의 `RequestBudget`(요청마다 하나)이 맡는다. 피드 조회의 의존성 호출은 `budget.call("<의존성>") { gateway... }`로 시작하고 `budget.await(future)`(실패를 던진다)나 `budget.awaitResult(future)`(실패를 `Result`로 돌려준다. 등급대로 대체할 의존성은 이쪽)로 기다린다. 대체는 `FeedDegradation.compose`가 받은 `Result`로 한 곳에서 한다. 마감이 지나면 끝나지 않은 호출을 `TimeBudgetExhaustedException`으로 먼저 끝내므로 `IsolatedCalls`의 실패 로그와 겹치지 않는다. 예산이 없으면(`weave.feed.time-budget` 없음) 상한 없이 기다린다.
- 대체 경로는 `FeedAssembler` 한 곳이다. 대체(`FeedDegradation.compose`), 캐시 읽기, 대체 로그를 모두 요청 스레드에서 한다. 대체 로그는 `FallbackLog`로 대체한 의존성마다 한 요청에 한 줄(`fallback_applied`)이고, 200이면 `compose`의 영역 결과(`sections`)에서 골라 응답의 `degradation`과 어긋나지 않게, 503이면 던지기 전에 남긴다. 실패 원인은 `downstream_call_failed` 줄에 있으니 다시 적지 않는다.
- 대체 지표는 `DegradationMetrics`(Bean, 기본값 `DISABLED`) 한 곳에서 만들고, 만들 때 모든 태그 조합을 0으로 등록한다(대시보드·degrade 비율이 첫 대체 전에도 시계열을 본다). 영역 결과와 post 캐시 읽기는 `FeedAssembler`가, 쓰기(비동기 결과)는 `PostStaleCache`가 센다. 태그를 더하면 등록 목록(`SectionOutcome`, `PostCacheRead.TAGS`, `PostCacheWrite`)도 같이 바꾼다.
- 시각은 `Clock` Bean(`ClockConfig`, `systemUTC`)에서 읽는다. 예산, user 캐시 유효 기간(Caffeine `Ticker`), post stale 판단이 같은 시계를 쓰고 테스트는 `MovableClock`으로 바꾼다. `FeedAssembler`에 더하는 협력 객체는 기본값(예: `UserProfileCache.DISABLED`, `PostStaleCache.DISABLED`)을 둔다. 커밋된 단위 테스트가 생성자를 직접 부른다.
- post stale 캐시(`degradation.PostStaleCache`)는 읽기를 요청 스레드에서 동기로(상한은 `spring.data.redis.timeout`), 쓰기를 자기 전용 스레드 하나로 한다. 대체할 수 없으면 `PostsUnavailableException` → `FeedController`의 503이다. 실행기는 Bean으로 두지 않는다(`Executor` Bean이 생기면 Boot의 `applicationTaskExecutor`가 빠져 semaphore 모드가 깨진다). Lettuce `ClientOptions`는 `LettuceClientOptionsBuilderCustomizer`(Boot 4 `org.springframework.boot.data.redis.autoconfigure`)로 Boot가 만든 빌더에 더한다(`PostStaleCacheConfig`).
- Spring 없이 도는 단위 테스트의 로그는 JSON이 아니라 logback 기본 형식(`event="..." cause="..."`)이다. `LogCapture.jsonLines()`가 비므로 `lines()`의 `raw`를 본다(`FeedAssemblerBudgetTest`).
- 실패 원인(`cause`)은 `DownstreamFailure.of` 한 곳에서 정하고, 서킷이 실패로 세는지(`DownstreamFailure.countsAsCircuitFailure`)도 같은 분류를 쓴다(add-call-isolation design 결정 7). 응답 타임아웃(원인이 `SocketTimeoutException`)과 TimeLimiter의 `TimeoutException`은 `timeout`, 서킷이 막은 호출은 `circuit_open`, 벌크헤드 거절은 `bulkhead_full`, 요청 시간 예산 초과(`TimeBudgetExhaustedException`)는 `budget_exhausted`, 요청 수 상한(`RequestNotPermitted`)은 `rate_limited`, Retry-After 대기(`RetryAfterHoldException`)는 `retry_after`다. 다시 부를지는 `RetryPolicy.retryable`(5xx, `connect_failure`, 풀 대기를 뺀 `io_failure`)이 같은 분류로 정한다. 커넥션 풀 대기 시간 초과(`org.apache.hc.core5.http.ConnectionRequestTimeoutException`)는 `io_failure`이고 `connect_failure`와 섞지 않는다. 연결 시간 초과(`ConnectTimeoutException`)도 `SocketTimeoutException`이지만 `connect_failure`다.
- 호출 지표(`http.client.requests`)의 `client_name`은 호스트가 아니라 HTTP 서비스 그룹 이름(`post` 등)이다(`HttpClientConfig.groupNameClientMetrics`). 대시보드·리포트 질의는 이 값으로 의존성을 가른다.
- 그룹의 요청 팩토리는 Boot가 아니라 `ConnectionPoolMetrics`(configurer 순서 `HIGHEST_PRECEDENCE + 20`)가 마지막에 다시 만들어 넣고, 커넥션 풀 지표(`httpcomponents_httpclient_pool_*{httpclient="<그룹>"}`)를 묶는다. 요청 팩토리를 바꾸는 configurer를 더하면 이 순서와 겹치지 않게 한다.
- 연결·응답 타임아웃은 Boot 그룹 설정(`spring.http.serviceclient.<그룹>.connect-timeout`, `read-timeout`)이다. Boot에 없는 것은 `HttpClientProperties`(`weave.http-client.*`)에 둔다. 모든 그룹 공통 값은 `clientHttpRequestFactoryBuilder` Bean에, 그룹별 값(`groups.<그룹>.max-connections`)은 `ConnectionPoolMetrics`가 그룹마다 Bean 빌더 뒤에 더한다(Boot 빌더의 `with...Customizer`는 앞 것에 이어 붙어 뒤 것이 덮는다).
- post 캐시(Redis)를 쓰는 테스트는 `PostCacheRedis`(Testcontainers Redis 하나를 JVM에서 같이 쓴다, `registerAddress`·`flush`·`awaitKey`·`warmUp`)를, 시계를 옮기는 테스트는 `@Import(MovableClockConfiguration::class)`와 `MovableClock.advance`를 쓴다. 테스트 기본 Redis 주소는 듣지 않는 포트(`localhost:1`)다.
- 하위 서비스 오류 응답의 예외 메시지에는 본문이 없다(`HttpClientConfig.bodylessErrorMessages`). 본문이 필요하면 `getResponseBodyAsString()`이나 `getResponseBodyAs(...)`(그 클라이언트의 메시지 변환기로 읽는다)로 읽고, 로그에는 남기지 않는다. 예외 객체를 로거에 넘기지 않는다.
